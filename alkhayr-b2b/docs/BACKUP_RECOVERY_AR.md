# دليل النسخ الاحتياطي والاستعادة واسترداد الحسابات (المرحلة 15)

هذا الدليل لمشغّل الخادم فقط. كل الأوامر تُنفَّذ **على جهاز الخادم نفسه** من سطر الأوامر؛ لا يوجد أي مسار عبر
الموقع لاسترداد كلمة مرور أو مُصادِق أو لتنزيل نسخة احتياطية، ولا يوجد حساب استرداد افتراضي. صلاحية
الدخول إلى نظام تشغيل الخادم هي سلطة الاسترداد الوحيدة.

> صيغة الأوامر: داخل مجلد التطبيق `npm run cli -- <الأمر> [الخيارات]`
> (في نسخة الإصدار: `node --env-file-if-exists=.env dist/server/cli.js <الأمر> [الخيارات]`).
> الأوامر الموثقة هنا مُختبرة آلياً (انظر «ما الذي اختُبر» في آخر الدليل).

---

## 1. القواعد التي لا تُكسر

1. **لا يُكتب أي سر في سطر الأوامر**: لا مفتاح النسخ، ولا كلمة مرور، ولا رمز مُصادِق، ولا APP_SECRET.
   الأوامر ترفض أي خيار غير معروف وترفض صيغة `--x=value` (رمز الخروج 2). الأسرار تُكتب في موجّه مخفي
   (لا يظهر ما تكتبه) أو — لمفتاح النسخ فقط — من **ملف مفتاح محمي**.
2. **انتظر ظهور الموجّه المخفي** قبل الكتابة. السطر «Password rules: …» معلومات وليس موجّهاً.
3. **APP_SECRET ومفتاح النسخ سرّان منفصلان** يُحفظان في مكانين مختلفين، وليس في مجلد النسخ نفسه.
4. **النسخة المحلية ليست حماية**: النسخ في `BACKUP_DIR` على نفس القرص. انسخها دورياً إلى مكان آخر خارج الخادم.
5. لا تُشغّل أوامر الاستعادة أو الحسابات على قاعدة بيانات حقيقية «للتجربة». تدرّب على مجلد بيانات جديد.

## 2. الأسرار وحفظها

| السر | ما الذي يحميه | أين يُحفظ | ماذا يحدث إن ضاع |
|---|---|---|---|
| `APP_SECRET` (في `.env`) | الجلسات وCSRF وحدود المعدل، **وتشفير سر المُصادِق (TOTP) لكل مدير** | ملف `.env` على الخادم + نسخة محمية خارج الخادم (خزنة كلمات مرور للمؤسسة أو ظرف مختوم) | لا يمكن فك أسرار المُصادِق؛ الخادم يرفض البدء؛ انظر الحالة (هـ) |
| مفتاح النسخ (ملف `backup.key`) | تشفير ملفات النسخ الاحتياطي | ملف `0600` خارج `DATA_DIR` و`BACKUP_DIR` + نسخة محمية خارج الخادم **منفصلة** عن نسخ الملفات | **لا يمكن استعادة أي نسخة مشفرة به**؛ انظر الحالة (د) |

- `BACKUP_KEY` في `.env` **لم يعد مستخدماً** (المرحلة 15). اتركه فارغاً.
- **تدوير APP_SECRET غير مدعوم.** تغييره يجعل كل مُصادِقات المديرين غير قابلة للفك. لا تغيّره.
- **تسجيل أي سر يخص أي نسخة**: كل نسخة تحمل في رأسها `keyId` (بصمة مفتاح النسخ) و`appSecretId`
  (بصمة APP_SECRET) — بصمات قصيرة لا تكشف السر. سجّل في سجل التشغيل: «المفتاح ذو البصمة X ← مخزّن في Y».
  اعرض البصمات بـ `backup:inspect` (القسم 4).
- **اختبار أن APP_SECRET الحالي يفك المُصادِقات**: `backup:verify` يفحص ذلك (السطر `"mfa": "readable"`).
  الخادم نفسه يرفض البدء إن لم يستطع فك سر مدير.

### إنشاء مفتاح النسخ (مرة واحدة)

```sh
sudo install -d -m 700 -o alkhayr /etc/alkhayr-keys        # مجلد خاص خارج DATA_DIR و BACKUP_DIR
npm run cli -- backup:keygen --out /etc/alkhayr-keys/backup.key
```
- يُنشئ 32 بايت عشوائية في ملف `0600`، ولا يطبع المفتاح؛ يطبع بصمته فقط. لا يكتب فوق ملف موجود.
- يرفض الإنشاء داخل `DATA_DIR` أو `BACKUP_DIR`.
- عند القراءة يُرفض الملف إن كان: رابطاً رمزياً، أو مملوكاً لمستخدم آخر، أو مقروءاً لغير المالك، أو داخل مجلد البيانات/النسخ.
- انسخ محتوى الملف فوراً إلى خزنة خارج الخادم (لا تنسخه بجانب ملفات النسخ).

## 3. أخذ نسخة احتياطية

```sh
npm run cli -- backup:create --key-file /etc/alkhayr-keys/backup.key --keep 14
```
- يعمل **والخادم يعمل** (لقطة متسقة عبر واجهة SQLite للنسخ، تشمل ما في WAL؛ مُختبرة تحت كتابات متزامنة).
- الخطوات: لقطة إلى مجلد مؤقت خاص داخل `DATA_DIR` ← تحقق كامل ← تشفير AES-256-GCM بمفتاح فرعي ونونس
  جديدين لكل نسخة ← كتابة ذرّية `0600` ← **فك تشفير النسخة النهائية والتحقق منها مرة أخرى** ← علامة «متحقَّق منها».
- عند أي فشل: لا يبقى ملف ناقص، ولا تُمس النسخ السابقة، ويُحذف المجلد المؤقت.
- `--keep 14` اختياري: يحتفظ بأحدث 14 نسخة **وبأحدث نسخة متحقَّق منها دائماً**، ولا يحذف إلا ملفات بالاسم المُدار
  `alkhayr-YYYYMMDD-HHMMSS-xxxxxxxx.akbk` (لا يتبع الروابط الرمزية ولا يلمس ملفات أخرى).
- بدون `--key-file` يُطلب المفتاح في موجّه مخفي: `Backup key (hidden):`.
- ما تحتويه النسخة: قاعدة البيانات كاملة (كل الجداول، سجل الترحيلات، سجل التدقيق، سجلات منع التكرار).
  ما لا تحتويه: الكود، بيانات المتصفح، ملف `.env`، الأسرار، الملفات المؤقتة.

### الجدولة (اختيارية)
للتشغيل غير التفاعلي استخدم `--key-file` فقط (ملف محمي كما سبق)، مثلاً عبر cron لمستخدم `alkhayr`:
```
17 2 * * *  cd /opt/alkhayr && node --env-file-if-exists=.env dist/server/cli.js backup:create --key-file /etc/alkhayr-keys/backup.key --keep 14
```
لا يرفع النظام أي نسخة إلى خدمة خارجية تلقائياً. النسخ خارج الخادم مسؤولية المشغّل (مثلاً `rsync` لملفات
`.akbk` فقط إلى جهاز آخر؛ الملفات مشفرة ولا تحتاج حماية إضافية للمحتوى، لكن **لا تضع المفتاح معها**).

### المراقبة
```sh
npm run cli -- backup:status
```
يطبع JSON: عدد النسخ، عمر أحدث نسخة وأحدث نسخة متحقَّق منها، حجم القاعدة وملف WAL، أعداد الصفوف، المساحة الحرة،
بقايا التشغيلات المقطوعة. رمز الخروج **3** يعني وجود تحذير (لا نسخة متحقَّق منها، أو أحدثها أقدم من 26 ساعة،
أو بقايا). مناسب لربطه بالمراقبة في المرحلة 17.

## 4. فحص نسخة والتحقق منها

```sh
npm run cli -- backup:inspect /var/backups/alkhayr/alkhayr-20261113-021700-1a2b3c4d.akbk
npm run cli -- backup:verify  /var/backups/alkhayr/alkhayr-20261113-021700-1a2b3c4d.akbk --key-file /etc/alkhayr-keys/backup.key
```
- `inspect`: يعرض بيانات الرأس **قبل** التحقق (تاريخ، إصدار المخطط، `keyId`، `appSecretId`) ولا يحتاج مفتاحاً.
- `verify` يفك التشفير في مجلد مؤقت خاص ويتحقق من:
  - وسم المصادقة (GCM) وبصمة المحتوى؛
  - هوية القاعدة؛
  - `integrity_check` و`foreign_key_check`؛
  - بصمات الترحيلات؛
  - الثوابت: رصيد كل منتج = آخر حركة في دفتره = مجموع حركاته، والمحجوز = الحجوزات المفتوحة، وعدد عناصر
    كل استيراد، ولكل مدير مُصادِق؛
  - إمكانية فك مُصادِقات المديرين بـ APP_SECRET الحالي.
- ثم يضع علامة «متحقَّق منها».
- الأخطاء عامة وآمنة، مثل:
  - `KEY_MISMATCH` مفتاح آخر؛
  - `AUTH_FAILED` ملف معدَّل أو تالف؛
  - `TRUNCATED`؛
  - `VERSION_UNSUPPORTED`؛
  - `DB_CORRUPT`؛
  - `SCHEMA_INCOMPATIBLE`؛
  - `INVARIANT_FAILED`؛
  - `APP_SECRET_MISMATCH`.
- **لا يُصلح شيئاً**؛ النسخة الفاشلة لا تُستعاد.

## 5. الاستعادة

```sh
# 1) أوقف الخادم.
# 2) استعد إلى مجلد بيانات جديد (مُفضّل):
DATA_DIR=/srv/alkhayr/data-restored npm run cli -- backup:restore /var/backups/alkhayr/alkhayr-20261113-021700-1a2b3c4d.akbk --key-file /etc/alkhayr-keys/backup.key
# 3) شغّل الخادم على المجلد الجديد (اضبط DATA_DIR في .env)، تحقّق، ثم صالح البيانات مع العمل.
```
- يرفض العمل إن كان الخادم يعمل على المجلد الهدف (`INSTANCE_LOCKED`).
- يرفض إن وُجدت قاعدة في الهدف (`TARGET_EXISTS`). للاستبدال الصريح أضف `--replace`:
  تُنقل القاعدة الحالية (مع `-wal`/`-shm`) **كما هي** إلى `DATA_DIR/pre-restore-<وقت>-<رمز>/` ولا تُحذف أبداً.
- يتحقق من النسخة **كاملاً قبل** لمس الهدف. لا استبدال جزئي: عند أي فشل يبقى الهدف كما كان.
- يرفض نسخة من إصدار أحدث (`SCHEMA_TOO_NEW`). لا ترحيل صامت: إن كانت النسخة أقدم يطبع أمر `db:migrate` لتشغيله يدوياً.
- لا يدمج بيانات؛ يستبدل النقطة الزمنية كاملة.

### ما يحدث للوصول بعد الاستعادة
| العنصر | الأثر |
|---|---|
| الجلسات | **تُحذف كل الجلسات المستعادة**: كل مستخدم يسجّل الدخول من جديد؛ ملفات تعريف الارتباط القديمة مرفوضة |
| منع إعادة استخدام رمز المُصادِق | محفوظ (`last_otp_step`)؛ الرمز المستخدم قبل النسخة يُرفض |
| حدود المعدل | تعود إلى حالتها وقت النسخة (عدّادات قصيرة العمر؛ لا أثر أمني يُذكر) |
| سجلات منع التكرار (طلبات، استيرادات) | **محفوظة ولا تُحذف**: إعادة إرسال نفس الطلب بنفس المفتاح تعيد الطلب الأصلي إن كان في النسخة |
| رموز معاينة الاستيراد | صالحة 20 دقيقة فقط ومربوطة بالبيانات؛ عملياً منتهية أو مرفوضة لاختلاف النسخة |
| عمليات متصفح غير محسومة | طلب أُرسل بعد وقت النسخة **غير موجود** في البيانات المستعادة؛ إعادة الإرسال بنفس المفتاح قد تُنشئه من جديد ← **راجع مع التاجر قبل فتح البوابة** |
| التدقيق | يُضاف سجل `backup.restored` بفاعل فارغ (إجراء مشغّل/نظام)، دون اختلاق مدير |

### وضع الاستعادة (المرحلة 16)
بعد أي استعادة تبدأ البوابة في **وضع الاستعادة**:
- يعمل تسجيل الدخول والتصفح، وتعمل إعادة إرسال عملية موجودة في البيانات المستعادة (تُعرض نتيجتها الأصلية).
- تُرفض كل عملية جديدة (طلب، حركة مخزون، استيراد، تعديل منتج أو إعدادات، اعتماد تاجر، تعديل ملف، تسجيل
  حساب) برسالة «وضع الصيانة» دون تنفيذ أي شيء.
- تحصل كل استعادة على **رقم حقبة** جديد. أي عملية جُهّزت في المتصفح قبل الاستعادة، وليست موجودة في البيانات
  المستعادة، تُرفض نهائيًا حتى بعد إعادة الفتح (`RECOVERY_EPOCH_STALE`). يجب على المستخدم المراجعة من جديد
  وإنشاء عملية جديدة؛ لا يُعاد إرسال شيء تلقائيًا.

```sh
npm run cli -- recovery:status          # writeMode: recovery | open (رمز الخروج 3 أثناء الاستعادة)
npm run cli -- db:check                 # فحص الاتساق (قراءة فقط)
npm run cli -- recovery:reopen          # بعد المصالحة: سبب + كتابة REOPEN؛ يُسجَّل في التدقيق
```
- `recovery:reopen` يرفض إذا وُجدت أخطاء اتساق، ويمكن تشغيله والخادم يعمل.
- **إعادة الفتح لا تعيد بناء أي شيء مفقود.** على العمل مصالحة الطلبات والتسليمات والمخزون من مصادر خارجية،
  ثم إدخال الناقص كعمليات جديدة.

### المصالحة بعد الاستعادة (إلزامية)
البيانات المستعادة **نقطة زمنية أقدم**. كل ما حدث بعد النسخة مفقود: طلبات، حركات مخزون، استيرادات، حسابات،
تغييرات حالة. قبل فتح البوابة للتجار:
1. حدّد وقت النسخة (`backup:inspect` ← `createdAt`).
2. اجمع ما حدث بعده من مصادر العمل: رسائل التجار، فواتير، محاضر التسليم، الجرد الفعلي.
3. أعد إدخال ما يلزم عبر الشاشات المعتادة أو الاستيراد (مثلاً «تعيين الرصيد الفعلي» بعد جرد).
4. أبلغ التجار بإعادة تسجيل الدخول والتأكد من طلباتهم في «طلباتي».

## 6. أوامر الحسابات (الخادم متوقف)

كل أوامر الحسابات:
- **تفاعلية** وتحتاج طرفية حقيقية؛
- تتطلب إيقاف الخادم (قفل النسخة الواحدة)؛
- تعرض الحساب ثم تطلب **إعادة كتابة اسم المستخدم للتأكيد** و**سبباً** (3–200 حرف) يُسجَّل في التدقيق؛
- تتبع سياسة كلمات المرور نفسها وتجزئتها نفسها؛
- لا تُغيّر الدور ولا حالة الاعتماد؛ ولا تحوّل تاجراً إلى مدير أبداً؛
- لا تحفظ شيئاً عند الإلغاء (Ctrl-C) أو بعد ثلاث محاولات خاطئة.

كل تغيير يرفع رقم `credential_version` (الترحيل 0007). لذلك أي تسجيل دخول كان قيد التنفيذ بالبيانات القديمة يُرفض
عند الحفظ، حتى لو تحقق من كلمة المرور قبل التغيير.

```sh
npm run cli -- account:reset-password    # كلمة مرور جديدة (مخفية مرتين)؛ تُلغى كل جلسات الحساب
npm run cli -- account:reset-mfa         # مدير فقط: مُصادِق جديد يُثبت برمز قبل الحفظ
npm run cli -- account:revoke-sessions   # إنهاء كل جلسات الحساب دون تغيير بيانات الدخول
npm run cli -- admin:create              # مدير إضافي جديد (setup-admin للمدير الأول فقط)
```

## 7. حالات الاسترداد (أ – و)

**(أ) مستخدم نسي كلمة المرور**
- تحقق من هويته خارج النظام (اتصال من الرقم المسجل، حضور شخصي).
- ثم `account:reset-password`. تُلغى جلساته، وتُرفض كلمة المرور القديمة.
- سلّمه كلمة المرور الجديدة عبر قناة آمنة، ويستطيع تغييرها من «الملف الشخصي».

**(ب) مدير فقد المُصادِق (هاتف ضاع أو تغيّر)**
- تحقق من هويته شخصياً، ثم `account:reset-mfa`.
- المُصادِق القديم يبقى صالحاً **حتى** يُثبت الجديد برمز صحيح. بعد الحفظ يتوقف القديم وتُلغى الجلسات.
- لا يوجد تجاوز للمُصادِق.
- إن فقد المدير الوحيد كلمة المرور والمُصادِق معاً: نفّذ الأمرين على الحساب نفسه.
- أو أنشئ مديراً آخر بـ `admin:create`؛ الأمر يتطلب إثبات مُصادِقه الخاص.

**(ج) ضاع الخادم أو القرص، وتوجد نسخة + المفتاح + APP_SECRET**
- جهّز خادماً جديداً بنفس الإصدار (أو أحدث) وضع `APP_SECRET` الأصلي في `.env`.
- انسخ ملف `.akbk` وملف المفتاح (بشكل منفصل).
- ثم `backup:verify` ← `backup:restore` إلى `DATA_DIR` جديد ← `db:migrate --confirm-backup` إن طُلب ← شغّل الخادم ← المصالحة (القسم 5).

**(د) ضاع مفتاح النسخ**
- **النسخ المشفرة به غير قابلة للاستعادة.** لا يوجد باب خلفي.
- إن كان الخادم سليماً:
  1. أنشئ مفتاحاً جديداً فوراً (`backup:keygen` بمسار جديد).
  2. خذ نسخة جديدة وتحقق منها.
  3. احفظ المفتاح الجديد خارج الخادم.
- النسخ القديمة بلا قيمة بعد ذلك.

**(هـ) ضاع APP_SECRET**
- لا يمكن فك مُصادِقات المديرين، ولا يُولَّد سر بديل فوق الأسرار المشفرة تلقائياً، ولا يُعطَّل المُصادِق بصمت.
- المسار الصريح الوحيد:
  1. ضع `APP_SECRET` جديداً في `.env`.
  2. استعد بـ `--accept-new-app-secret`، وهو يرفض بدونه (`APP_SECRET_MISMATCH`).
  3. **الخادم يرفض البدء** حتى يُعاد تسجيل مُصادِق كل مدير بـ `account:reset-mfa` (بعد التحقق من هويته شخصياً).
- الجلسات تُلغى بأي حال. كلمات المرور لا تتأثر (scrypt لا يعتمد على APP_SECRET).
- إن لم تكن هناك حاجة لاستعادة: الخادم الحالي لن يبدأ. احصل على نسخة حديثة ثم اتبع المسار أعلاه.
  أو ضع السر الجديد ونفّذ `account:reset-mfa` لكل مدير على القاعدة الحالية والخادم متوقف.

**(و) اختراق حساب مدير أو الخادم**
- حساب مدير مُخترق:
  1. `account:revoke-sessions` ثم `account:reset-password` ثم `account:reset-mfa` للحساب.
  2. راجع سجل التدقيق.
- خادم مُخترق:
  - اعتبر `APP_SECRET` ومفتاح النسخ (إن كان على الخادم) وكل كلمات المرور مكشوفة.
  - ابنِ خادماً نظيفاً، واستعد من نسخة **قبل** الاختراق.
  - ضع APP_SECRET جديداً (الحالة هـ)، وأعد تسجيل مُصادِقات كل المديرين، وأعد تعيين كلمات المرور.
  - أنشئ مفتاح نسخ جديداً.
  - **النظام لا يستطيع وحده إثبات خلو نسخة من التلاعب** إن كان المهاجم يملك المفتاح.

## 8. الاحتفاظ والتنظيف

| البيانات | السياسة |
|---|---|
| النسخ الاحتياطية | `--keep N` (مقترح 14 يومياً) + نسخ دورية خارج الخادم بقرار المشغّل؛ أحدث نسخة متحقَّق منها لا تُحذف أبداً |
| سجل التدقيق | 365 يوماً على الأقل؛ **لا حذف آلي** في هذه المرحلة |
| سجلات الاستيراد ومنع التكرار | **تُحفظ بلا حد**؛ لا تُحذف لمجرد قدمها |
| الطلبات ودفتر المخزون | تاريخ تجاري دائم؛ لا حذف |
| الملفات المؤقتة | المجلدات المؤقتة وملفات `.partial` الأقدم من ساعة تُحذف تلقائياً في النسخة التالية (بالأسماء المُدارة فقط، دون تتبع روابط رمزية) |

**قياس النمو** (مرحلة 15، بيانات اصطناعية):
- 2000 طلب بسطر واحد = نحو 3.2 ميغابايت، أي **≈ 1.6 كيلوبايت لكل طلب**، شاملة الفهارس والأحداث والحجوزات والدفتر.
- لم يُقس نمو سجلات الاستيراد بعد. راقب `backup:status` (حجم القاعدة وأعداد الصفوف).

## 9. أهداف الاسترداد (RPO / RTO)

- **تنبيه (المرحلة 16):** القيمتان التاليتان أهداف **مؤقتة مقترحة**، لم يعتمدها أصحاب العمل ولم تُقَس على بيانات حقيقية.
- **RPO (أقصى فقد مقبول) — هدف وليس قياساً:** 24 ساعة مع نسخة يومية. أقل من ذلك يتطلب نسخاً أكثر تكراراً.
- **RTO (زمن العودة) — هدف:** ساعتان من توفر خادم بديل ونسخة ومفتاح وAPP_SECRET، دون وقت المصالحة التجارية.
- **المقاس فعلاً:** في تمرين آلي على بيانات اصطناعية صغيرة جداً، استغرق «استعادة + تحقق + بدء الخادم» نحو 0.3 ثانية.
  **هذا ليس RTO لبيانات حقيقية.** قِس تمرينك الخاص على نسخة من الحجم الحقيقي في مجلد منفصل.

### تمرين دوري مقترح (شهري)
1. `backup:verify` لأحدث نسخة.
2. استعادة إلى مجلد جديد على جهاز اختبار باستخدام نسخة المفتاح و APP_SECRET **المحفوظة خارج الخادم**؛ هذا يثبت
   أن الأسرار المحفوظة صحيحة.
3. تشغيل الخادم على المجلد، ودخول مدير بالمُصادِق الأصلي، ودخول تاجر ومراجعة طلباته.
4. حذف مجلد الاختبار. تسجيل الزمن في سجل التشغيل.

## 10. ما الذي اختُبر

اختُبر آلياً، في قواعد بيانات ومجلدات مؤقتة فقط:
- `tests/integration/backup.test.ts` (عبر نفس دالة الأوامر):
  - إنشاء المفتاح وصلاحياته؛
  - الإنشاء والفحص والتحقق؛
  - المفتاح الخاطئ، الملف المعدل أو المقطوع، الإصدار غير المدعوم، الرأس الضخم، وAPP_SECRET الخاطئ؛
  - قاعدة تالفة أو غير متوافقة داخل حاوية سليمة؛
  - الاستعادة إلى مجلد جديد، ورفض الهدف العامل أو الموجود، و`--replace`؛
  - فشل الاستعادة والنسخ دون أثر، والتدوير، والحالة؛
  - الحالة (هـ)؛
  - النسخ أثناء كتابات متزامنة.
- `tests/integration/recovery-cli.test.ts`:
  - `admin:create`، والإلغاء، والرمز الخاطئ؛
  - رفض الترقية ورفض العمل والخادم يعمل؛
  - إعادة تعيين كلمة المرور والمُصادِق وإلغاء الجلسات؛
  - سباقات مع تسجيل دخول متوقف مؤقتاً؛
  - مشغّلات الترحيل 0007.
- `tests/integration/restore-drill.test.ts` (خادم وأوامر حقيقية):
  - نسخة أثناء عمل الخادم، ثم استعادة إلى `DATA_DIR` جديد، ثم بدء حقيقي؛
  - دخول المدير بالمُصادِق الأصلي، ودخول التاجر وسجل طلباته؛
  - إعادة الإرسال بنفس المفتاح، ورفض الجلسات القديمة، ورفض APP_SECRET الخاطئ؛
  - وفي طرفية حقيقية (PTY): مفتاح النسخ مخفي لا يظهر، وإعادة تعيين كلمة مرور.
- **المرحلة 16:** اختُبرت الأوامر عبر `npm run cli --` في طرفية حقيقية: إنشاء مدير، وإعادة تعيين كلمة المرور والمُصادِق، وإلغاء الجلسات، والنسخ والتحقق والحالة، و`db:check` و`recovery:status` و`recovery:reopen`.
- **لم يُختبر:** جدولة cron، والنسخ خارج الخادم، والاستعادة على نظام Windows، والأحجام الكبيرة.
