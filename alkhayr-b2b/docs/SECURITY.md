# ALKHAYR — Security Policy (contract)

Status: **Policy defined in stage 00; controls implemented so far are listed in §12 with the stage
that tested them (03: password hashing, TOTP, secret encryption, administrator bootstrap; 04: login,
registration, sessions, CSRF, request boundaries, rate limits, authorization guards; 05: merchant profile ownership, administrator review/approval, access versioning; 06: product administration and the approved catalog; 07: inventory adjustments and ledger).** Historical results from
the earlier 2.0.1 project (22 tests / zero advisories) do **not** apply to this codebase.

## 1. Prohibited in every build
- Guest ordering, default admin, first-user-is-admin, hardcoded/test logins, review-mode/preview bypass.
- Trusting identity/role headers (e.g. ChatGPT/OpenAI user headers, `X-User-Role`, `X-Merchant-Id`).
- Auth tokens in localStorage/sessionStorage; tokens in URLs.
- Wildcard CORS with credentials (no CORS at all: same-origin SPA).
- HTTP endpoints for backup download, restore, admin creation, password or MFA reset.
- Generated fallback secrets. Placeholder secrets in production → startup failure.
- Mock/fake success responses standing in for real backend behaviour.

## 2. Passwords (implemented stage 03: `src/server/auth/passwords.ts`)
- Node `crypto.scrypt`, N = 131072 (ln = 17), r = 8, p = 1, 16-byte CSPRNG salt per password, 32-byte key.
- Explicit `maxmem` = 128·N·r·p + 1 MiB (≈ 129 MiB per hash; the exact 128·N·r is refused by OpenSSL).
  Measured here ≈ 350 ms per hash.
- Versioned encoding `$scrypt$v=1$ln=17,r=8,p=1$<salt>$<hash>`. Stored hashes are parsed strictly
  (exact layout, canonical base64url, exact lengths) and executed **only if their parameters are on an
  allow-list** (currently just the reference set). Inflated (e.g. ln=30, r=64, p=16), weaker or unknown
  parameters are rejected before any scrypt work.
- Bounded work: at most 2 concurrent hashes and 32 queued per process; further requests are rejected
  immediately with `PasswordHasherBusyError` (stage 04 maps it to 503/429). Peak ≈ 258 MiB.
- Constant-time comparison (`timingSafeEqual`). `verifyDummy()` performs one full verification at the
  current parameters through the same limiter for unknown usernames (stage 04).
- Policy: traders ≥ 12, administrators ≥ 15, at most 128 characters (grapheme clusters) **and** 512 UTF-8
  bytes. Passwords are NFC-normalized (identical visible text in different Unicode compositions matches)
  but **never trimmed, lowercased or truncated**: over-limit input is rejected. No composition rules;
  no breached-list lookup (no external calls).
- Plaintext passwords are never stored, logged, echoed or accepted as command-line arguments (tested).

## 3. Administrator MFA (implemented stage 03: `src/server/auth/totp.ts`)
- RFC 6238 TOTP: 20-byte CSPRNG secret, HMAC-SHA1, 6 digits (leading zeros kept), 30 s period,
  verification window ±1 period (previous, current, next). Exactly 6 ASCII digits are accepted.
- `verifyTotp` returns the **accepted time step**. Replay protection is persistent, not in memory:
  stage 04 performs `UPDATE auth_users SET last_otp_step = ? WHERE id = ? AND (last_otp_step IS NULL OR last_otp_step < ?)`
  and requires exactly one affected row. `verifyTotp` can also exclude steps ≤ a known last step.
- Verified against RFC 4226 Appendix D and RFC 6238 Appendix B vectors plus explicit period boundaries.
- Enrollment (`setup-admin`) shows the base32 secret and `otpauth://` URI **only in the operator's
  terminal**, warns against third-party QR generators, requires a valid code before saving, and stores
  that code's step as `last_otp_step`. No HTTP route returns MFA secrets.

## 4. Keys and secret encryption (implemented stage 03: `src/server/auth/encryption.ts`)
| Key | Source | Use |
|---|---|---|
| `APP_SECRET` | ≥ 32 random bytes (base64url), generated by the operator locally | HKDF-SHA256 (salt `alkhayr/kdf/v1`, info `alkhayr:<purpose>:v1`) → independent 32-byte keys for `totp`, `csrf`, `cursor`, `ip`, `rate_limit` |
| `BACKUP_KEY` | independent 32 random bytes | Backup encryption (stage 15). Never derived from APP_SECRET; must differ from it. |
- MFA secrets: AES-256-GCM, fresh 12-byte random nonce per encryption, 16-byte tag, AAD
  `alkhayr:totp:v1:<user id>` (a ciphertext copied to another user fails). Envelope `v1.<b64url(nonce‖ct‖tag)>`.
- Rejections: `MALFORMED` (layout/non-canonical encoding/too long), `UNSUPPORTED_VERSION`, `TRUNCATED`,
  `AUTH_FAILED` (wrong key/AAD/tampering). No partial plaintext is ever returned.
- Configuration: production refuses to start with missing, placeholder, low-entropy, short or identical
  secrets (stage 01). Since stage 04 the **server requires APP_SECRET in every mode** (sessions, CSRF,
  rate-limit keys and MFA depend on it); only the database CLI commands run without it. No fallback key
  is ever generated.
- **Key mismatch:** if an administrator's MFA secret cannot be decrypted with the configured APP_SECRET,
  the server refuses to start (`MFA_KEY_MISMATCH`, or `APP_SECRET_REQUIRED` if none is set) and tells the
  operator to restore the original key. It never replaces the secret, disables MFA or resets the account.
- SQLite itself is **not** encrypted at rest; disk encryption is a hosting responsibility. Database
  directory 0700 and files 0600 (stage 02).

## 4a. Administrator bootstrap (implemented stage 03: `setup-admin`)
- Local CLI only, interactive terminal required (refused when stdin is not a TTY), no arguments accepted.
- Requires APP_SECRET, an existing database at the current schema version, and the instance lock
  (server stopped). Never creates or migrates a database.
- Refuses if any administrator exists; refuses usernames already used by any account (never promotes).
- Hashing, TOTP proof and encryption happen before the single write transaction, which re-checks the
  preconditions and creates user + approved profile + `admin.bootstrap` audit event atomically.
  Cancellation (Ctrl-C/Ctrl-D), failed proof, conflicts or errors save nothing.
- Hidden input enters raw mode before the prompt is displayed (no echo; Ctrl-C handled, not a signal).

## 5. Sessions & cookies (implemented stage 04: `src/server/auth/sessions.ts`, `cookies.ts`)
- Token: 32 CSPRNG bytes (base64url, 256 bits), sent only in the cookie; the database stores only
  SHA-256(token). Tokens never appear in JSON, URLs, logs or browser storage.
- Cookie (production): `__Host-alkhayr_session`; `Path=/; HttpOnly; SameSite=Strict; Max-Age=28800; Secure`;
  no Domain. Development/test over plain http use `alkhayr_session` without Secure (D-007).
  A cookie name appearing twice in a request is treated as absent (anti cookie-tossing).
- Validity is re-checked on **every** request against server time and current rows: absolute 8 h;
  idle 15 min (admin) / 30 min (trader); `sessions.password_changed_at = auth_users.password_changed_at`;
  merchant profile present and not suspended. Invalid sessions are deleted and the cookie expired.
- Idle touch: `last_seen_at` is written at most once per minute (effective idle precision ≈ 1 min) by a
  conditional UPDATE that re-checks expiry, so a session can never be revived.
- Login rotates: a new token is always issued and any presented session (valid or not, any account)
  is deleted. At most 5 sessions per account: the login transaction drops expired ones and keeps the
  4 newest before inserting (serialized by BEGIN IMMEDIATE, so concurrent logins cannot exceed 5).
- Password change revokes **all** sessions of the account (including the current one).
  Suspension takes effect on the next request (session lookup refuses it; stage 05 also deletes rows).
- Privileged administrator operations call `requireRecentAdminAuth`: credentials (password + TOTP)
  verified within 15 min (`auth_at`), else `428 RECENT_AUTH_REQUIRED`; the remedy is a normal login.

## 6. CSRF, origin and fetch metadata (implemented stage 04: `auth/csrf.ts`, `http/request-guards.ts`)
- Session token `s1.` + HMAC-SHA256(csrfKey, "session\0" + raw session token): bound to one session,
  different per session, nothing stored (D-030).
- Pre-login token `p1.<expiry>.` + HMAC(csrfKey, "prelogin\0" + nonce + "\0" + expiry), bound to the random
  10-minute pre-session cookie (`__Host-alkhayr_presession`), accepted only by login/registration,
  never as a session token; it grants no authentication. Lifetime cannot be extended by the client.
- Every `/api` request: `Sec-Fetch-Site`, when present, must be `same-origin` (or `none` for GET/HEAD).
- Every mutation: `Origin` must equal `APP_ORIGIN` exactly (missing → refused); `application/json` only;
  CSRF header as above. `Host` must equal the configured host for every request. No CORS.

## 7. Request hardening and abuse limits (implemented stage 04: `auth/rate-limit.ts`, `http/client-ip.ts`)
- Body limit enforced while streaming (auth routes 8 KiB, default 64 KiB, import 2 MiB later) → 413.
- Server timeouts: `headersTimeout` 15 s, `requestTimeout` 30 s, keep-alive 5 s; max header 16 KiB.
- Order of work on login/registration: boundary → general limit → bounded body → strict schema → CSRF →
  login/registration limits → only then scrypt (which has its own 2-running/32-queued cap → 503).
- **Persistence:** counters are rows in the SQLite `rate_limits` table, so they survive an application
  restart (tested with the real bundled server: 5 failures, restart, 6th attempt → 429). Only the
  password-hashing concurrency limiter (§2) is in memory. No distributed store is used or needed for the
  single-instance deployment.
- **Keyed pseudonyms:** each key is HMAC-SHA256 under the rate-limit purpose key
  (HKDF(APP_SECRET, info `alkhayr:rate_limit:v1`)) over `bucket + "\0" + identifier`; audit IPs use a separate
  `alkhayr:ip:v1` key. Without APP_SECRET the values cannot be enumerated from IPs/usernames. This has been
  the scheme since stage 04, so no stored-key transition was needed. If APP_SECRET is ever rotated, existing
  counters simply stop matching (limits restart from zero) — a deliberate, documented effect.
- Durable fixed-window counters in `rate_limits`, keyed as above (no raw IP/username/password stored):

  | Bucket | Limit | Identifier |
  |---|---|---|
  | `login_ip` | 20 / 15 min | client IP (IPv6: /64) |
  | `login_account` | 5 / 15 min | normalized username (existing or not); reset on successful login |
  | `register_ip` | 5 / hour | client IP |
  | `password_account` | 5 / 15 min | account |
  | `order_create_account` | 30 / 10 min | merchant (stage 08) |
  | `order_quote_account` | 60 / 10 min | merchant (stage 11, read-only quote) |
  | `api_ip` | 300 / min | client IP, every `/api` request |

  Denied attempts do not extend the window; `429` carries `Retry-After` (seconds to window end).
- Bounded growth: at 100 000 live rows, expired rows are purged; if still full, new identities share
  one restrictive overflow counter per bucket. A background sweep (every 60 s, 5 000 rows per pass)
  removes expired counters and sessions.
- **Availability trade-off — OPEN, not solved:** anyone can exhaust a username's 5 attempts per
  15 minutes and so delay that user's login (no permanent lockout; nothing reveals whether the account
  exists). Per-IP limits apply to all users behind one NAT/proxy address. Operators should watch
  `rate_limited` log events. **Carried to stage 16 (adversarial review) and to the release gate (stage 18)**
  as an explicit risk to accept or mitigate (e.g. separate limits for previously-successful devices).
- `TRUST_PROXY`: exact proxy IPs. `X-Forwarded-For` is honoured only when the TCP peer is one of them,
  read right-to-left skipping trusted hops; malformed data → the peer address. Otherwise the socket
  address is used, so direct clients cannot spoof their address. The app port must not be reachable
  except through that proxy (stage 17).

## 7a. Merchant data ownership and administration (implemented stage 05)
- Self-service profile: the merchant is always the session's own; no id is accepted in path, query or
  body (strict schemas; any query parameter → 400). Editable: business name, contact name, optional
  email, phone, governorate, address — same normalization as registration. Status, role, credentials,
  MFA and `access_version` are not writable. `expectedVersion` prevents stale overwrites (409 with the
  newer data, never last-write-wins).
- Administrator endpoints require a live administrator session; status changes additionally require
  recent authentication (≤ 15 min, re-checked at commit) and the session-bound CSRF token. Reads do not
  require recency (D-063).
- Status changes run in one transaction: re-validate the administrator, re-read the target, check
  `expectedVersion` and the transition table, update status + `version` + `access_version`, delete the
  target's sessions when access is removed (→ suspended, approved → pending), audit. Failure of any part
  rolls everything back (tested with injected revocation and audit failures).
- Administrator accounts cannot be suspended/demoted (403 `ADMIN_ACCOUNT_PROTECTED`); no endpoint changes
  roles, passwords or MFA; nothing deletes history.
- Every mutation re-validates the session at commit (`revalidateAtCommit`), so a suspension, logout,
  password change or lapse of recency while the body is in flight prevents the write (tested).
- ABA: login compares `merchants.access_version` read before verification with the value at commit.
- List queries: strict parameters, allow-listed sorts mapped to fixed SQL, bound values, LIKE wildcards
  escaped, keyset pagination with HMAC-signed cursors bound to administrator, sort and filters.
- Audit: `merchant.profile_updated` stores changed field NAMES only; `merchant.status_changed` stores
  from/to, the administrator's reason, revoked-session count and version. No profile values or secrets.

## 7b. Products and catalog (implemented stage 06)
- Catalog reads (`/api/v1/products…`, `/api/v1/catalog/filters`) require a session whose merchant is
  **approved** (checked live per request); pending → 403, suspended/anonymous → 401. Only active products
  are returned; inactive and unknown ids give the identical 404. Traders never receive on_hand, reserved,
  available numbers, versions, timestamps or audit data — only an availability status.
- Product administration: reads need a live administrator session; create/update need recent
  authentication (≤ 15 min) and the session CSRF token, all re-validated at commit (slow bodies tested).
- Input types are validated by strict zod schemas **before** SQLite could coerce them: integers only
  (no strings, booleans, fractions, NaN/±Infinity, unsafe integers), bounded lengths and ranges,
  unknown fields rejected (stock, reservation, id, version, timestamps, demo on update).
- Stock cannot be changed through product endpoints; creation starts at zero; stage 07 owns stock.
- Optimistic concurrency uses two independent layers: an `expectedVersion` pre-check and an UPDATE
  `WHERE version = <client expectedVersion>`; each alone blocks stale writes (mutation-tested). The same
  binding was applied to the stage-05 merchant updates.
- Barcode uniqueness: pre-check plus the database unique index (mapped to 409 `DUPLICATE`).
- Image URLs: https only, no userinfo (`@` anywhere in the authority is refused), no whitespace or
  backslashes, ≤ 2048 chars, stored canonically. **The server never fetches image URLs** (no proxy, no
  download, no uploads). Images are hosted by the business; the UI must load them with
  `referrerpolicy="no-referrer"` (the site-wide `Referrer-Policy: no-referrer` header already applies)
  and show truthful placeholders when missing. CSP `img-src 'self' https: data:` limits schemes.
- Demo products: only outside production, fixed at creation; never convertible to/from real.
- No DELETE endpoints; products referenced by history are protected by `ON DELETE RESTRICT`.
- Search and filters: bound parameters, fixed sort allow-list, literal LIKE (`%`, `_` escaped),
  exact barcode/brand match, HMAC cursors bound to user, endpoint (catalog vs admin), sort and filters;
  filter choices derived only from active products.

## 7c. Inventory (implemented stage 07)
- Reads (`/api/v1/admin/inventory…`) need a live administrator session; adjustments need recent
  authentication (re-checked at commit, also for idempotent replays), the session CSRF token, exact
  Origin, JSON and an 8 KiB body.
- Strict per-type schemas (receipt / correction_delta / set_total); integers validated before SQLite;
  reserved, available, balances, order, actor and product fields are rejected. Manual adjustments never
  change `reserved`; receiving stock never activates a product.
- One transaction: re-validate → idempotency lookup (per administrator, SHA-256 digest of the meaningful
  request) → `expectedVersion` → balance rules → ledger row → linked product update `WHERE version =
  expectedVersion` → audit. Any failure rolls everything back and leaves the operation key unused.
- **Database-enforced since 0003:** products are inserted inactive with zero stock; every on_hand/reserved
  change must be paired with a new matching ledger row (deltas, balances, version) — for every write path.
  Exact boundary: DATABASE.md §12.
- Audit `inventory.adjusted` stores type, delta, resulting on_hand, version and the ledger id; reason and
  reference live in the append-only ledger.

## 7d. Orders (implemented stage 08)
- `POST /api/v1/orders`: session + session CSRF + exact Origin + JSON (32 KiB); approved merchant only;
  the merchant is always the session's own (no id from body, path or headers; administrators order only
  for their own approved profile). Re-checked at commit: valid session for the same user, still approved,
  `merchants.access_version` unchanged since the request started (ABA-safe).
- Strict schema; collection limit (100 lines) before any other validation; integers validated before
  SQLite; server-owned fields (merchant, actor, buyer, state, totals, tax, shipping, reservation, demo,
  version, display number) rejected.
- Server-authoritative prices, packaging, availability, demo classification, tax, shipping and buyer
  snapshot; client prices/packaging are stale-data checks only. BigInt arithmetic, half-up tax, limits
  rejected not clamped.
- Idempotency per merchant (`UNIQUE(merchant_id, request_key)` + SHA-256 digest); replay before any
  current-state rule; concurrent identical requests serialize on `BEGIN IMMEDIATE` (one order).
- No stock counts disclosed: insufficient-stock errors carry only the availability status. Exact
  availability can still be **bounded** by repeated attempts with different quantities; the per-merchant
  limit of 30 attempts / 10 min (counted for every attempt, valid or not) slows this probing (T57).
- Reads: approved own-merchant only, finalized orders only, identical 404 for foreign/unfinished/unknown
  ids, signed cursors bound to user + merchant + filter, no digests or revenue claims.
- Audit `order.created` stores display number, line count, total and demo flag only (no note or buyer data).
- Database finalization guards (0004) make the creation event a consistency check; exact boundary DATABASE.md §13.

## 7e. Order fulfillment (implemented stage 09)
- Reads (`/api/v1/admin/orders…`): live administrator session. Transitions: recent authentication (15 min,
  re-checked at commit and before returning a replay), session CSRF, exact Origin, JSON, 4 KiB, strict body.
- Own-order routes stay merchant-scoped; administrators see other merchants' orders only through the
  separate administrator routes.
- Idempotency per administrator (`order_events (actor_user_id, operation_key)` unique + digest); replay before
  version/state checks; nothing reapplied.
- Concurrency: `BEGIN IMMEDIATE`; client `expectedVersion` pre-check, `WHERE version = expectedVersion`, and
  the event's `order_version_after` check (database). Concurrent different operations from one version:
  one commits, the others get 409.
- Per-order reservations (`order_allocations`) make it impossible — at the database level — to ship or
  release stock reserved for another order. Exact boundary: DATABASE.md §14.
- Packaging cannot change while stocked or reserved (service 409 + database trigger); confirmation refuses
  orders whose snapshot pack size differs from the product's.
- Buyer suspension blocks forward processing (service + database) but never cancels or releases
  automatically; cancellation needs a reason; delivery of shipped orders stays possible.
- Administrators see stock counts in conflicts; traders still see only availability statuses.
- Audit `order.transitioned`: from, to, version, event id, movement kind, line count (reason in the event).

## 7f. Browser application (implemented stage 10)
- Same-origin cookie authentication only; the client refuses non-API URLs and never persists session,
  password, MFA or CSRF values in browser storage or cookies (tested on source and bundles).
- Distinct session vs pre-login CSRF types; mutations are never retried automatically; a network failure
  of a mutation is reported as "outcome unknown — retry the same request".
- Navigation visibility (admin/merchant/pending) is presentation only; authorization stays on the server.
  No administrator data is requested before `/auth/me` identifies an administrator.
- No `dangerouslySetInnerHTML`, `innerHTML`, `eval`/`new Function` in `src/web` (test); React escaping
  is the stored-XSS control for names, notes and addresses (T14).
- CSP unchanged (no `unsafe-inline`/`unsafe-eval`, fonts and scripts `'self'`); fonts bundled locally;
  no remote stylesheet/script/font (tests reject `@import` and non-`/assets` CSS URLs).
- The development component gallery and its synthetic fixtures are excluded from production builds
  (separate entry point; tested on the bundles and in a browser).
- Product images: `img-src https:` already allowed; loaded with `referrerPolicy="no-referrer"`, lazy,
  with a placeholder on failure; never fetched server-side.

## 7g. Merchant experience (implemented stage 11)
- Sign-in: one generic failure for every cause (unknown user, wrong password, suspended, wrong/missing
  OTP). The OTP field appears only when the user chooses "administrator sign-in"; an administrator signing
  in without it gets the same generic failure (no account discovery). A fresh pre-login token is fetched
  for every sign-in/registration attempt, even when a session exists. Usernames/passwords are sent as
  typed; codes keep leading zeros. Passwords/codes are cleared from component state after each attempt and
  are never stored, logged or put in URLs. No password-reset, MFA-recovery or "remember me" feature exists.
- Registration: allowed fields only, pending trader only, identical response for duplicates, no automatic
  sign-in, no claim that any message was sent.
- Identity changes (sign-in as another account, logout, expiry, suspension): the whole signed-in UI is
  keyed by user+merchant and remounted; 401 removes protected UI; 403 `ACCOUNT_PENDING`/`ACCESS_CHANGED`
  re-reads identity; a page restored from the back/forward cache re-checks identity. A failed identity
  request is shown as a network failure, never as "signed out"; a failed logout is reported, never hidden.
- Pending traders never request catalog or order data (verified in the browser).
- **Browser storage (reconciled with SPEC §7):** only `src/web/cart/storage.ts` may use storage
  (enforced by tests). It stores the cart draft and at most one pending submission (request key + exact
  payload) under `alkhayr.v1.draft.<userId>.<merchantId>` in localStorage — no tokens, passwords, codes,
  buyer data or responses; validated on read; 7-day expiry; removed on explicit logout, on successful
  submission and, for other accounts, when a different identity signs in. Residual risk: anyone with access
  to the browser profile can read product ids/quantities/reviewed prices of a draft (accepted in the threat
  model since stage 00).
- Orders: one request key per intended submission, stored with its exact payload before sending; unclear
  outcomes (no response, 5xx, malformed response) keep both for an explicit same-request retry; definite
  refusals release the key; nothing is retried automatically. A changed cart is a new payload with a new
  key, allowed only after the previous outcome is resolved or deliberately discarded.
- Checkout quote: approved merchants only, session CSRF + Origin + JSON, strict body, per-merchant limit;
  writes nothing; returns merchant-safe amounts (no settings dump, no stock counts).
- Traders still see no stock counts, administrator names or cancellation reasons.

## 7h. Administration experience (implemented stage 12)
- Administration screens mount only inside the administrator shell (after `/auth/me` reports an
  administrator); traders reaching `#/admin/*` get the forbidden view and the browser run verified that no
  trader context requested `/api/v1/admin`. The server authorizes every call regardless (stages 05–09).
- Reads need a live administrator session; every mutation needs recent authentication (15 min), enforced by
  the server (428). The client answers 428 with a **dedicated** sign-in panel (password + new TOTP code, fresh
  pre-login token, real login endpoint); it never wraps credentials in a generic confirmation component, never
  stores passwords, codes, CSRF or session tokens, and never executes the prepared action afterwards — the
  operator re-reads the record and confirms again (new key).
- Operation keys (inventory adjustments, order transitions, order requests) come from `crypto.getRandomValues`
  only; without it nothing is sent (explicit message). Keys and exact payloads of unclear operations stay in
  memory for a same-key retry; a key is never regenerated because a response was lost, and an edited form is
  never sent under an old key.
- Non-idempotent administrator writes (product create/edit, merchant status) are never retried automatically.
- No repair, delete or history-editing control exists: the ledger and order history are read-only in the UI;
  corrections are new reversing movements with a reason. Consistency recovery stays in stage 16.
- No seeded/default administrators, no first-user-is-admin, no administrator-creation or recovery feature;
  the only bootstrap is `setup-admin` on the host (refuses a second administrator).
- Barcodes are sent exactly as typed (empty → `null`); prices are converted from decimal pounds to piastres
  with integer arithmetic and extra precision is refused (never rounded); image URLs must be https without
  credentials (the server re-validates and never fetches them). All text is rendered through React escaping.
- Unchanged open risks: username lockout (T40) and slow stock inference (T57/T73).

## 8. Headers
`Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' https: data:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'; object-src 'none'`
(any `style-src 'unsafe-inline'` exception must be justified in DECISIONS.md),
`X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`,
`Cross-Origin-Opener-Policy: same-origin`, `Permissions-Policy` minimal, HSTS (via proxy in production),
`Cache-Control: no-store` on API responses. No remote fonts/CDNs in production (fonts self-hosted).

## 9. Data access
- Parameterized SQL only; sort/filter via allow-lists; no string-built SQL from input.
- Ownership enforced in the query (`WHERE merchant_id = :sessionMerchant`), not only after fetch.
- Not-owned resources return 404.

## 10. Logging & audit
- No passwords, tokens, cookies, CSRF values, TOTP codes, secrets or login bodies in logs (tested).
- Authentication audit actions (stage 04): `auth.register`, `auth.register_duplicate`, `auth.login`,
  `auth.login_failed` (internal `reason`: unknown_user, bad_password, mfa_failed, suspended,
  stale_credentials, otp_replay, …), `auth.logout`, `auth.password_changed`, `auth.password_change_failed`.
  Reasons are stored for operators only and never returned to clients.
- IP stored only as HMAC(ipKey, ip). Audit retention: at least 365 days — younger rows cannot be deleted (database trigger), older rows only by an explicit operator purge, never automatically (D-014). Rate-limit rows are disposable (≤ 30 days).
- Audit metadata uses allow-listed keys per action.

## 11. Supply chain
- Pinned versions in `package-lock.json`; minimal dependency set; `npm audit` run and dated in
  stage 16 (discloses dependency metadata to the registry — noted). SBOM + license notices in release.
- No claim of "zero vulnerabilities" without a dated scan; scans do not cover OS images unless run.
