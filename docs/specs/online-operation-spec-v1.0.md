# Online Operation & Ordering — Module Specification v1.0

Source: blueprint §13 (Online Operation & Ordering) + its integration note,
§21.1 (معيار التكامل), §22 (Availability). Module scope per §5 table:
**Online Operation = Ticketing + Order Issues/Requests integration
readiness**.

Open points are flagged as assumptions F1–F6.

## 1. Blueprint requirements (verbatim mapping)

| §13 item                | Delivered as                                                                        |
| ----------------------- | ----------------------------------------------------------------------------------- |
| Daily Orders            | `OnlineOrder` records ingested via the Integration Layer slot; daily count in stats |
| Order Issues            | Universal tickets of new type `ONLINE_ISSUE` (F1)                                   |
| Order Requests          | Universal tickets of new type `ONLINE_REQUEST` (F1)                                 |
| Handled Issues/Requests | Stats: tickets of each type resolved in the selected day                            |
| Open / Closed           | Ticket status kinds (engine, ADR-003)                                               |
| Request Source          | `RequestSource` catalog + nullable `requestSourceKey` on Ticket (F3)                |
| Order Source            | `OrderSource` catalog on `OnlineOrder` (F3)                                         |
| Assigned Agent          | Ticket `responsible` (engine, ADR-004)                                              |
| Handling Time           | createdAt → resolvedAt; average in stats                                            |
| SLA Achievement         | % of the day's resolved online tickets without SLA breach (engine)                  |
| Retry Queue + Monitor   | `IntegrationOperation` queue + retry sweeper + Integration Monitor (F5)             |

## 2. Design decisions

### F1 — Issues/Requests ride the Universal Ticket Engine (ADR-003)

The §5 scope line says it directly: Online Operation is **Ticketing** plus
integration readiness. `ONLINE_ISSUE` / `ONLINE_REQUEST` become TicketType
catalog rows (data, not code). Everything §13 lists per record — assignment,
open/closed, updates, mandatory resolution, SLA timers, timeline, audit,
queues and filters — is inherited with zero new workflow code. The existing
`relatedOrderNo` ticket field (§9.4) links a ticket to its order; the online
module joins it against `OnlineOrder.externalNumber`.

### F2 — Categories for the online types

§13 does not enumerate categories, and the ticket engine requires one. One
generic seeded category per type (`GENERAL` — "مشكلة طلب" / "طلب خدمة")
keeps us inside the blueprint; operations can add real categories through
the existing ticketing-config catalog without deployments (ADR-008). SLA
policies for both types are generated by the existing type×urgency seed.

### F3 — Source catalogs

"Request Source" and "Order Source" are listed without values. Both become
editable catalogs seeded with a minimal starter set (APP / WEBSITE /
CALL_CENTER); `OnlineOrder.orderSourceKey` is required on ingest,
`Ticket.requestSourceKey` is a new **nullable** column filled for online
tickets (existing flows untouched).

### F4 — Order ingest (integration readiness)

Same pattern as performance spec D1: the Ordering System connector is Later
(§23), so the readiness half ships now — `POST /online/orders/ingest`
(idempotent upsert by `externalNumber`, per-row rejection reasons,
audit-logged, permission `online.ingest` granted to INTEGRATION_SUPPORT).
No manual order entry: orders are integration-owned data (§13).

### F5 — Retry Queue + Integration Monitor (the §13 resilience note)

> عند تعطل التكامل لا يتوقف النظام، بل تسجل العملية في Retry Queue ويظهر
> تنبيه في Integration Monitor.

This lands as a shared engine (§8 Integration Engine foundation):

- `IntegrationOperation` rows: integrationKey, operation, payload, status
  `PENDING → SUCCEEDED | FAILED → … → DEAD`, attempts, nextRetryAt,
  lastError.
- `IntegrationsService.enqueue()` — callers never block on the external
  system: they enqueue and move on (§22 Availability).
- Retry sweeper (same in-process pattern as SLA/Breaks;
  `INTEGRATION_SWEEP_INTERVAL_SECONDS`, 0 = disabled for tests) with
  exponential backoff (`integrations.retry.base_delay_seconds` ×2 per
  attempt) up to `integrations.retry.max_attempts`, then **DEAD** +
  in-app alert to platform admins — the Monitor alert made real.
- Executor: HTTP POST to `integrations.ordering.endpoint` (§21.1 Timeout,
  Error Mapping, Request/Response Logging via lastError/audit). While the
  endpoint setting is empty the operation fails and retries — which is
  exactly the degraded-mode behaviour §13 describes; the future connector
  simply fills the setting (ADR-009).
- First real producer: resolving an `ONLINE_ISSUE`/`ONLINE_REQUEST` ticket
  enqueues `ordering.issue_resolved` (outbound sync slot) — gated by
  `integrations.ordering.outbound_enabled` (default **false** so a
  non-configured system stays quiet).
- Monitor API: per-integration health (counts by status, last success /
  last failure), operations list, manual retry. Permission
  `integration.monitor` (admins + INTEGRATION_SUPPORT).

### F6 — Stats endpoint, not a new reporting engine

`GET /online/stats?date=` returns the §13 counters for one day: dailyOrders,
open/closed & handled per type, avg handling minutes, SLA achievement %.
The Reporting Engine (§8) with drill-downs stays a later phase; agent-level
performance already lives in the §12 dashboard.

## 3. Data model

```
OnlineOrder            externalNumber (unique), orderSourceKey → OrderSource,
                       orderedAt, customerName?, customerPhone?, value?,
                       externalStatus?, createdAt/updatedAt
OrderSource            key, nameAr, nameEn, active     (editable catalog)
RequestSource          key, nameAr, nameEn, active     (editable catalog)
Ticket                 + requestSourceKey String? → RequestSource (F3)
IntegrationOperation   integrationKey, operation, payload Json,
                       status PENDING|SUCCEEDED|FAILED|DEAD,
                       attempts, nextRetryAt, lastError?, timestamps
                       @@index(status, nextRetryAt), @@index(integrationKey, createdAt)
```

## 4. API surface

```
POST /online/orders/ingest        online.ingest        idempotent batch upsert (F4)
GET  /online/orders               online.view          list (date/source/search filters)
GET  /online/stats                online.view          §13 day counters (F6)
GET  /online/catalogs             online.view          order/request sources
GET  /integrations/monitor        integration.monitor  health per integration
GET  /integrations/operations     integration.monitor  operations list (status filter)
POST /integrations/operations/:id/retry  integration.monitor  re-queue now
```

Issues/requests use the existing `/tickets` API (`typeKey: ONLINE_ISSUE|
ONLINE_REQUEST`, optional `requestSourceKey`, `relatedOrderNo`).

## 5. Permissions & settings

| Key                   | Defaults                                                          |
| --------------------- | ----------------------------------------------------------------- |
| `online.view`         | Agent MY_TEAM, Sup/Leader MY_TEAM, Manager DEPARTMENT, admins ALL |
| `online.ingest`       | INTEGRATION_SUPPORT ALL_DATA, admins                              |
| `integration.monitor` | INTEGRATION_SUPPORT ALL_DATA, Business Excellence view, admins    |

Settings (category `integrations`): `integrations.ordering.endpoint` (STRING,
empty), `integrations.ordering.outbound_enabled` (BOOLEAN, false),
`integrations.retry.max_attempts` (NUMBER, 5),
`integrations.retry.base_delay_seconds` (NUMBER, 60).

## 6. Out of scope (explicitly)

The physical Ordering System connector (Later, fills the endpoint setting),
order content/lines (integration-owned), DBS availability (§21 table),
Reporting Engine dashboards (§8 later), webhooks inbound signature scheme
(defined with the connector).
